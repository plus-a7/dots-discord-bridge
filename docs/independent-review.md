Reviewed the bridge implementation, README, installed SDK behavior, dependency lockfile, and offline tests. No credentials, external connections, Discord posts, listeners, or dot subscriptions were used. This report concerns the offline implementation, not production approval.

## Result

The six findings from the first review and the later `guild_owner` owner-reconfiguration finding are addressed. No unresolved blocking issue was identified within the reviewed offline scope.

| Original finding | Current correction |
| --- | --- |
| Crash leaves an exclusive lock file permanently blocking restart | A separate SQLite `BEGIN EXCLUSIVE` connection holds an OS-managed lock, released when the process exits. |
| Unsubscribe during callback verification can be undone by subscribe | An unsubscribe generation is checked after verification before activation. |
| Owner stop during channel preparation can still send a reply | The sender invokes the authorization guard after channel fetch, immediately before `channel.send`. |
| Individual Discord HTTP timeouts do not cap rate-limit waits | Rate limits are rejected; a total reply deadline invalidates the pre-send guard and returns `uncertain`. The concurrency gate stays held until the sender settles. |
| Crash after the fifth persisted callback reservation permits a sixth attempt | Dispatch checks the persisted attempt cap before posting. |
| Reusing a case ID for a different destination exposes stored old messages | Read and dispatch compare the full guild/channel/thread tuple against current configuration. |

## Limits and operational acceptance gates

A callback or Discord request already handed to the network cannot be recalled. Owner stop blocks pending preparation and subsequent operations; it cannot promise withdrawal of a request already in flight. A timeout therefore reports `uncertain`, never a fabricated success. Repeated reply calls do not resend an uncertain result; reconciliation requires inspecting actual Discord state after approval.

Both `process.exit` without closing the store and actual `SIGKILL` child-process tests verify lock release and saved state reopening. These are not a power-loss or disk-failure test. HTTPS tests cover rejection and signature validation with mocks; a real TLS exchange, DNS rebinding simulation, production key rotation, Discord Gateway resume, and real rate-limit behavior were not exercised.

Fresh channel fetch plus `permissionsFor` is a checked access boundary, not a proven atomic authoritative ACL: guild/member/role state also depends on discord.js caches and Gateway updates. Permission-revocation timing and reconnection behavior require live acceptance tests. Cached reply status can still be returned after stop without sending or rereading source message contents.

The bearer principal is an offline authentication seam. Actual authentication for the intended dot and subscription in the intended chat must be verified during the separately approved integration. Callback verification and a `2xx` webhook receipt do not prove dot wake or response. Ordinary MCP tools also do not prove wake.

Before live acceptance, verify the intended bot identity and exclusive process ownership, guild/channel/thread tuple, Message Content intent, thread visibility and send permissions, HTTPS or an approved secure MCP tunnel, actual ChatGPT callback host, subscription lifecycle in the intended dot conversation, and a real same-thread round trip. Gateway events missed while disconnected are not replayed by this implementation (`cursor: null`).

### Findings corrected during review

- **H1 — P2, request cancellation:** the initial HTTP endpoint dropped the incoming request signal when reconstructing the SDK Request. Delayed ACL/challenge/channel preparation could therefore submit a new side effect after a timeout or client disconnect while the runtime remained running. The endpoint now preserves the signal, and the SDK's actual modern factory supplies that Request through `requestInfo`. The reviewed SDK source supplies the per-request context; no shared mutable request signal is used.
- **H2 — P2, response bound:** the initial loopback adapter accumulated `response.arrayBuffer()` before checking the byte limit, with no abort race during that read. It now bounds bytes and chunks while reading, races cancellation, cancels without awaiting an untrusted cancellation promise, and rechecks abort before writing the response.
- **H3 — P2, lingering handler capacity:** HTTP cancellation can release a socket/HTTP request before its custom MCP ACL work settles. Counting that work without capping it still permitted repeated canceled requests to accumulate pending handlers. The endpoint now admits at most eight custom async handlers, reserves each slot before awaiting, and holds it through cancellation until actual settlement. A ninth request cannot start another ACL lookup; slots return after settlement.
- The first 79-test independent run had one assertion failure: it assumed HTTP `pending` remained positive until a delayed subscription ACL settled. The SDK may finish the canceled HTTP request first. The test now tracks actual ACL completion and `EventsAdapter.isBusy()`, and the disconnect test likewise waits for the delayed ACL completion before asserting absence of effects. ### Reviewed safeguards and evidence

The Access validator uses an immutable fixed issuer/audience/owner-email policy and optional exact subject, requires RS256, rejects key-location headers and unsupported algorithms, verifies signatures before accepting claims, bounds token/JWKS sizes and key counts, checks unique public RSA signing keys and minimum modulus, and rechecks expiry/closure after delayed JWKS work. A drain timeout returns `pending: true` and retains the Store; a later `stop()` can close it after settlement. Runtime/worker instances cannot restart a stale generation.
